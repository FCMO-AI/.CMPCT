# J24G95b — Prospective verification-to-consumption custody falsifier
Date: 2026-10-30 UTC. **New separate question, preregistered before implementation**. Parent J24G95 O0 exactly documents that independently **trusted** whole-archive SHA-256 is a good immutable snapshot identity control; source-exact first tribunal has 3/3 hosts SUCCESS at `a3aeb6fb3d6738db3e6054b9e75679fdfb983e4e`. We must not mistake successful *prior* hashing for proof that a later pathname Reader consumes those same bytes.

## Question / competing frames
Does verification of an archive's pinned whole-file SHA before opening it with the actual CMPCT Reader guarantee authenticated interpretation if the underlying path contents are modified in between? **Hypothesis: no, regardless of inode/size stability**. Existing #836 already proved that inode+size can survive a same-inode content rewrite (general metadata observation), so this is not claimed as new. Specific new test targets the exact *complete-archive external trust → released Reader/preflight consumption* interface from J24G95. Different from #749's verified staging leaf publication ownership and #859's footer-guard oracle.

## Physical controls and prospective disproof
Build a fresh genuine installed CMPCT archive with Builder and three public Writer DELETE commits at N=16/128/4096; only work on generated temporary files. Record a separately pinned SHA256 of the intact archive; verify it **before** a deliberately scheduled edit. Overwrite the latest footer's previously unbound 8-byte `prev` with the grandparent (copy bytes directly from a separately preserved physically rewired control). Do not change file length, footer payload bytes, stored digest or CMA4 blobs. Check `stat().st_dev`, `st_ino`, and `st_size` before and after; track `st_mtime_ns` separately (not an immutable security proof). Then call unchanged installed public Reader `verify()/read()` and `preflight_archive` on that path and compare against intact logical control. Finally re-hash the *changed* bytes: it **must** differ from pinned SHA and an explicit recheck must refuse it. If any host blocks changed Reader interpretation, differs in member other than authentic skipped DELETE, or changes inode/size or protected payload digests, mark the case as FAIL/INCONCLUSIVE, do not weaken the oracle. Existing #856 shows the Reader normally accepts rewired states; this is a TOCTOU binding control, not a new decoder bypass.

## Competing controls and alternative explanations
A pre-open trusted digest check *only* attests the pre-open file. A second check after in-place edit rejects the attack, but repeating it before a later open still leaves an interval; no claim of fully immune strategy. Pinning fd/inode or size alone cannot prevent writes to the held inode by another authorized handle. A physically immutable copy, sealed owner, filesystem snapshot, per-read authenticated bytes, atomic verified-handoff or externally trusted commit identity are different candidate architectures and must charge entire copy/verification/authorization/rollback cost. Windows may use different inode semantics; preserve observation, no universal filesystem claim.

## Research rung / safety / scope
Small source-exact installed-API O0 three-host evidence, not proof of remote attack, real scheduler race, bypass of a *trusted digest checked on consumed bytes*, or new format. No writer/Reader/evaluator/format/release mutation. Existing source/code and prereg files immutable. Avoid applying this test to real paths. Preserve artifact/host IDs and an independent byte-level referee. No production adoption pending cross-process durable owner and recovery economics.
