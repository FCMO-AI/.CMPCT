# J24V03 — sparse hardlink verification: ownership and bounded memory (prospective)
Date: 2026-10-27 UTC. Source parent: J24V01 PR #613, exact 3b2bf3c2e033fa27d77b2355821dc0087aa46873, released baseline main@80c358f8824ec1b20d349c92ed94c898090969b0 (v0.30.0/r24). **This document precedes product edits and experiments.**
## Problem and scientific question
J24V01 improves regular K_FILE/S_SPARSE verify() but its explicit fallback for K_HARDLINK calls read() on the terminal sparse file, materializing full logical holes (and retaining decoded chunks). The same signed logical content is therefore verified through two inconsistent memory paths depending on entry kind. This is not the direct/symlink geometry repair #609 or the memoized strict preflight size admission #615.
Can a single operation-scoped, O(aliases+edges) resolver authenticate the terminal regular owner and enforce each hardlink alias logical size, then reuse the J24V01 streaming hash path for every sparse alias *without weakening verification frequency or accepting hostile cycles/targets*?
## Mechanisms, alternatives, controls
A: leave alias full-read (correct on ordinary valid archives but unbounded RSS); B: use fixed-window read_range (bounded output but repeated O(extent_count * windows) scans); C: resolve terminal owner once per alias graph with memoized O(N) path compression, check each intermediate signed alias size, reuse _verify_sparse_streamed on sparse-owner aliases, retain ordinary fallback for other modes. C is predicted to preserve exact SHA and lower peak RSS on legitimate 64MiB sparse owners with ≥1 hardlink. Do not cache successful SHA results across logical aliases: per-alias verification remains explicit, resisting semantic relaxation and competing with a stronger but riskier deduplicated proof-owner model.
Baseline control is exact J24V01 source, not synthetic estimates. Frozen independent v24 sparse vector and Builder-created authentic 64MiB sparse + os.link archive; duplicate index and footer resigning for adversarial alias sizes; signed forward and multi-hop alias references in lexical and reverse order. Independently verify physical payload unchanged after index mutation. Strong simpler control: regular file streaming path without alias. Alternative explanation: the Builder may have converted the file out of S_SPARSE or into a non-hardlink representation; reject any such evidence and do not claim memory savings.
## Prospective decisions / kill
1. Correct valid genuine r24 regular sparse+hardlink archives must still count and verify every logical member, including aliases.
2. Signed size mismatch at any alias hop, missing, wrong-kind and cyclic targets must reject; no positive integrity conclusion from simply changing in-memory rows without an independently reauthenticated archive.
3. Reader must not call read() to materialize any sparse owner or alias during verify; fresh-process Linux peak RSS on 64MiB owner+alias must be <128 MiB; existing J24V01 golden and 256MiB controls must stay unchanged and pass.
4. Memoized graph resolution must be bounded by O(aliases+edges), avoiding the historical quadratic chains of PR #342; test at least 512-chain lookup without repeated physical verification (tiny vector), and separately inspect wall/RSS for alias count and CPU hash work.
5. Abort/narrow on divergent logical SHA, acceptance of malformed signed alias, structural performance regressions, library/runtime provenance failures or change in original meaning of verify().

## Predicted lower-rung result
A fresh process verifying a 64MiB logical sparse owner+one alias under J24V01 needs >128MiB peak because the alias read() reconstructs holes, while candidate remains <128MiB. Source-exact ABBA CPU/wall is beneficial but not guaranteed; streaming zero hashes retain O(total verified logical bytes) CPU. The cheapest decisive evidence is one signed small-vector differential, then genuine sparse hardlink and subprocess VmHWM on Linux, then other hosts and complete benchmarks.
