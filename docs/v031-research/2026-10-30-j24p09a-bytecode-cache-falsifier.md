# J24P09a — Local falsifier: trusted source hash, untrusted executed bytecode

Date: 2026-10-30 UTC. **Post-prereg, unexpected negative**, discovered while J24P09 exact-head CI was independently running. This is a local inert Python subprocess result, **not** a hosted/release claim.

## Original claim that failed

The J24P09 initial candidate permitted pip-generated `__pycache__/*.pyc` to be ignored while asserting that all installed CMPCT Python package bytes matched the wheel. The proposed reason was that bytecode was merely generated from installed source. This is insufficient to prove what the Python runtime will execute.

## Differently rooted, source-independent falsifier

In one temporary directory, created a self-consistent synthetic wheel with `cmpct/__init__.py` containing `VALUE = 1`. Installed that same source path. Used `py_compile` to construct a timestamp-validated `.pyc`, preserved its 16-byte magic/flags/mtime/source-length header, but replaced its marshaled Python code object with benign `VALUE = 99`. Original installed `.py` bytes remained **identical to the wheel**. Executed a fresh Python subprocess with `PYTHONPATH` pointing to the isolated package, plus `PYTHONDONTWRITEBYTECODE=1` to exclude new cache writes.

Observed: initial attestor returned **PASS**, while `import cmpct; print(cmpct.VALUE)` printed **99** (exit 0). Python executed the cached code rather than the source bytes proven identical to the wheel. This is a local causal counterexample, not a real CMPCT compromise.

## Decision and least-complex repair

- **Falsified**: ignoring generated bytecode makes whole executable-package identity safe.
- `PYTHONDONTWRITEBYTECODE=1` alone does **not** help: Python still reads existing caches.
- Prospective bounded repair: official CI installations use `pip install --no-compile` and the attestor **rejects every installed `.pyc` / `__pycache__` file before CMPCT is imported**. The shipping wheel must not contain cached bytecode, either. Existing later smoke may generate source-derived caches only *after* attestation.
- Local cleaner positive on Python 3.13: `pip install --no-compile --no-index --no-deps` of exact previous official-style 777,657 B Linux wheel produces **zero** `.pyc` and zero `__pycache__` under installed `cmpct/`.
- Control remains real same wheel+installed files; changing any installed Python or native file must reject. New hostile cached Python code must reject without running it.
- Promotion still requires fresh exact-head 3-OS official-style wheels, 15 interpreter installs, evidence and no weakening of pre-existing gates.

## Scope and counterfactual

This narrows a previously imprecise claim, rather than rewriting the preregistration. The earlier possible discriminator was inspecting CPython's cache admission behavior, not benchmarking SHA speed. The lesson may generalize to other package-byte attestations, but no Discovery Engine policy change is earned from one case. No publisher-authentication, malicious OS or concurrent mutation claim.
