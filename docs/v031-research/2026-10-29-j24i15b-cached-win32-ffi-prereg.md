# J24I15b — cached Win32 FFI setup as a prospective causal confound falsifier

**Date:** 2026-10-29 UTC. **Status:** NEW PREDICTION BEFORE MODIFIED INSTRUMENT / no retrospective edits to J24I15 receipt. **Research scope only.**

## Original immutable result and newly exposed mechanism
J24I15 original installed Windows run [#40831313188](https://github.com/FCMO-AI/.CMPCT/actions/runs/40831313188) at exact SHA `9449f0f7bb32cf35b29d257960a3d5262b3d5935` produced 4/4 slower Win32 handle pairs, median B/A 1.973× in 256 files; original artifact #12878024229, detached referee reconstructed 64 actual timing samples and rejected 6/6 mutations. Its scientific claim is limited to the precise Python test as executed. After closing this original study, static code review exposed a **differently rooted experimental confound**: `win32_read_nofollow()` calls `api()` once **per file**, and `api()` creates two ctypes.Structure classes, looks up `WinDLL("kernel32")` and sets three function signatures for *every* B file. By contrast A's `os.stat` uses already initialized CPython APIs. This creates repeated user-space setup work that a correctly engineered Win32 adapter would cache once. Consequently the original negative cannot by itself rule out a cached no-follow-handle route.

## New falsifiable primary question
If the Win32 DLL and ctypes signature/struct declarations are initialized just once **outside timed trials**, without modifying the actual CreateFileW flags, handle-ownership, final reparse rejection, source bytes, four ABBA controls, or economic threshold, is B still 10% or more *faster* in at least 3/4 paired rounds on exactly the same deterministic 256-file family? Predict substantial relative improvement versus J24I15's B, but NOT automatically an overall safe speed win. Failure of both the physical safety controls or cost threshold retires this specific warmed-FFI implementation.

## Changed surface and strongest comparator
Create a new exact-head result from the original J24I15 test with one explicitly scoped change: add a single functools.lru_cache(maxsize=1) around `api()` and call `api()` exactly once before constructing the benchmark corpus or beginning timing. Keep the rest of the original instrument and A side verbatim; no change to nofollow semantics, held source bytes, file identity, SHA controls, repetitions, host or GitHub workflow. The old original immutable run remains the historical uncached control; do not compare absolute timings across independent hosts as a causal product victory. A and B *within the new run* are the decision-making A/B comparison. A/A ensures the host remains observable.

## Evidence decision / alternatives
A cheaper pure-code inspection suffices to show per-file initialization overhead is an instrumentation confound but not to establish its magnitude; an installed Windows rerun with preserved raw receipt is the cheapest honest material discriminator. If cached B still loses, retire leaf-only ctypes handle speed as an API design direction and continue owner #401 O47 or secure parent/root architecture. If cached B wins, still no product credit: stronger source-root confinement, `FileIdInfo` (ReFS), source mutation, filesystem metadata capture, sparse/CDC/deferred content and full Builder RSS/CPU/create/recovery remain mandatory.
