## Problem and new disproof

J24G11 same-installed physical court on GitHub Actions #40672948612 established 2.141x/2.181x faster exact irregular recovery than SQLite #664 at N=16,400 and no routine-case slowdown. But the packed array currently rebuilds itself *on every update*, making the claimed bounded-memory tier prone to quadratic Python merge traffic when short independent invalid ancestry paths arrive incrementally rather than one long chain. Previously untested structural generality; previously frozen J24G11 product claim must remain narrow.

Detached Python 3.13 model of *identical merge code and SQLite controls* (research rung, not CMPCT proof) generated 2-key incremental updates for N=20,000: packed ~5,006 ms and 32,892,944 repeated element visits, SQLite ~28.964 ms. One-shot 4,000 update: packed 2.715 ms, SQLite 2.268 ms. A genuine Reader product court could overturn this projection.

## Primary mechanism / alternatives

Hypothesis: when packed array already exists, hold at most 16,384 new distinct positions in existing `hot` set (whose membership is checked first); merge into sorted `array('Q')` only when hot threshold is crossed. This is amortized batch work, not an unlimited Python set. On crossing the fixed 1MiB total-position cap, spill BOTH packed and hot to original committed SQLite, with exact uint64 bijection and cleanup. `__len__` counts packed + hot to enforce original global limit. Preserve J24G11 hot-only + AP paths, all exact identities, same-source assumption and decoder semantics.

Simpler control: original #664 disk-backed SQLite, and bounded but unbatched J24G11 from exact original Reader blob; stronger unbounded Python set still fastest but increases RSS.
