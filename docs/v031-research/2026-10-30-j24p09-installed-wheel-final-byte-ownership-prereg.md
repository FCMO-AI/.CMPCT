## Primary question and mechanisms

Can a strict **post-retag, pre-install** wheel safety gate (#864 no-PEP427-`.data` + #854 macOS physical ARCH/RECORD/minOS) be composed with a **post-install, pre-smoke** full CMPCT-package byte identity check against the actual installed wheel, without falsely rejecting authentic Ubuntu/macOS/Windows wheels?

Previous #858 and #862 showed genuine pip success with .data/purelib overrides, including loader Python bytes that a native-only digest would miss. #863's general relocation map gave a false PASS on .data/data; #864 therefore rejects the whole .data surface. That guard alone is static: the installer or an existing environment could still produce installed bytes not represented by the wheel.

Prediction: on authenticated/current 23-member official-style CMPCT wheels, an interpreter-site installed package's **complete** `cmpct/` file set (excluding generated bytecode/cache) matches wheel `cmpct/` member paths and SHA-256 one-for-one; macOS checker accepts genuine universal2 and rejects arm64-only falsely tagged wheel; strict profile rejects .data relocation and path aliases. The build/CI gate must run on the **final retagged wheel** before pip, and the installed check must run before product smoke and any output receipt.

## Controls and falsifiers (freeze before implementation)

1. Original official-style Ubuntu/macOS/Windows wheels: unchanged installed `cmpct/` files PASS. Two different package baselines where possible.
2. Positive alternate valid file bytes **with corresponding wheel file bytes** PASS; this is identity checking, not static content allowlisting.
3. Negative: replace installed native bytes after wheel build => REJECT before import.
4. Negative: replace installed Python loader `cmpct/native_codec.py` only => REJECT even if native digest is unchanged.
5. Negative: add a previously unseen `cmpct/cmpct_core_old.so` => REJECT (except generated pycache files); catches stale loader ambiguity after upgrades.
6. Negative: remove any installed `cmpct/` wheel member => REJECT. Replacement by symlink or directory => REJECT.
7. Negative: mutate wheel after install => REJECT because wheel identity binds all installed expected bytes. A legitimate different wheel+install should PASS.
8. Guard preflight: #864 .data/purelib or .data/data injection REJECT; #854 incorrect Mach-O/RECORD REJECT. Retain all original guard controls.
9. Actual hosted 3-OS sdist-first **retagged** wheel, pip install, archive smoke, and source-SHA-associated receipt. All three must execute; a missing runner is infrastructure unknown, not product loss.
10. Audit path: wheel only from final retag output; exact one built wheel; no installation before guard, no repo-path import; compare installed regular files by opening them and hashing bytes; record wheel digest and source SHA.

## Stronger controls, alternatives and explicit kill conditions

- Stronger but more expensive: trust a signed publisher manifest and attest every installed distribution member (including `.dist-info` installer mutations) under OS-specific isolation. Not required to prove this incremental scoped contract, but necessary if signing or adversarial installer trust becomes a publication claim.
- Simpler: native-only SHA binding. Already falsified by #862 because malicious Python bytes may survive.
- Alternative: fully implement pip's relocations. #863 falsified that approach for this family; do not resurrect through aliases.
- Kill/narrow: a valid unmodified official CMPCT wheel with a clean isolated install fails; a changed Python loader passes; a stale native sidecar passes; an installed directory/symlink passes; a validator is run against a nonfinal intermediate wheel; or a completed job cannot bind receipts to the evaluated source/wheel bytes.
- Do not change frozen benchmarks, performance thresholds, release schema, canonical formatting, reader/writer, version, or published workflow owner branch.
- No security guarantee against a malicious OS, concurrently mutable site-packages, untrusted pip, a compromised build host, or malicious wheel signed by its publisher. These are out of scope; do not describe this as cryptographic publisher authentication.
- No claim of exact installed `.dist-info` identity; pip legitimately rewrites RECORD and may add metadata. Scope is all `cmpct/` package files.
- Roll forward success only after exact-head hosted receipt; local synthetic tests are O0 infrastructure evidence, not platform publication credit.
