## Question / worldview distance
Does strong verification certify **both** physically recorded redundant integrity facts (CRC32 and SHA-256), or only decoded SHA-256? Specifically, can a checksum-only corrupted but byte-exact, otherwise genuine r24 *direct RAW symlink* be accepted by compiled native `verify_complete()` while Python `verify()` rejects it?

This is a **different physical-checksum semantics** question from prior index SHA contradictions. It is not evidence of altered user data, physical SHA bypass, untrusted provenance, a new exploitable security vulnerability, or release regression by itself.

## Prospective prediction
On the authentic one-symlink RAW archive generated by the unchanged J24I30 fixture, flip exactly one bit of *only* the four-byte CMA4 CRC32 field (header offsets 28..31). Keep encoded primary/tail indexes, footer, CMA4 SHA-256, codec, compressed payload and decoded bytes **byte-identical**. Prediction: Python `CMPCT.verify()` rejects this physical CRC inconsistency, but native `Archive::verify_complete()` returns `Ok(1)` at #759 head because `checked_blob_layout` reads header SHA but does not compare CRC and `read_blob_range` hashes actual bytes.

## Simpler control / alternative explanations
Unchanged original must pass both readers and count one symlink. A one-bit *payload* flip must be rejected by both to show that this is not a generalized native SHA bypass. Physical detached auditor must prove (a) only CRC header changed, (b) original index/footer checksums authenticate, (c) original SHA-256 still matches decoded content, (d) only physical CRC is inconsistent. Strong alternative: native library may validate CRC in another path, in which case the hypothesis fails. Python may skip CRC in strong verify, in which case the purported interop difference fails.
