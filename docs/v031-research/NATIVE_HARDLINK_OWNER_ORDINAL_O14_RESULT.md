## Primary question and decision
**Can the authenticated revision-24 native index expose a terminal hardlink owner without client-specific parsers, over-reconstruction or recursive unbounded traversal?** **Yes, on the hosted genuine-Builder and independently reauthenticated hostile-index cases examined.** Added optional `cmpct_entry_hardlink_owner(archive, index, out_owner)`, valid only within the same live archive handle. The path-graph is iteratively resolved once at native open, compressing links to a terminal regular-file ordinal. It is NOT a byte read; ordinary hardlink `cmpct_entry_read_range` still returns `UNSUPPORTED`.

## Direct hosted evidence
- **11 results** in O14 JSON: seven independent signed malformed-target rejections plus explicit two-node cycle rejection, one valid multi-hop chain, and one 1,024-link star/chain cost experiment (count of JSON result records includes those experiment groups). Owner-to-`a.bin` and owner-to-`b.bin` real source graphs resolve to different correct native ordinals while both regular contents remain unchanged and independently verified against Python Reader.
- Invalid missing owner, self-cycle, two-node cycle, symbolic/directory owner, unsafe lexical owner, wrong size, wrong tuple shape and **nonexact backslash spelling of an existing canonical path** fail closed with native `FORMAT(-3)` at archive open. The last case is material: Python Reader resolves signed hardlink owner paths byte-exactly; canonical-alias fallback in Rust would otherwise invent a cross-reader mapping.
- Null archive, out-of-range index, null result pointer and nonhardlink return their documented C status. When `out_owner` is valid, errors set it to zero; a valid terminal owner with ordinal zero still returns success. No borrowed native pointers exported.
- **1,024 hardlinks, seven opens each:** terminal-owner chain archive 4,605 stored bytes; median native open `0.554359 ms` (raw `[0.570163,0.496721,0.551976,0.503032,0.554359,0.566828,0.610554]`). ## Strongest adversarial self-critique
The new graph resolver **rejects malformed authenticated hardlink graphs already admitted by some older readers**. Fail-closed behavior may be correct for a secure native preflight but cross-reader compatibility must be assessed before promotion. It enforces target spelling exactness to agree with Python's source semantics. It does not write physical hardlinks and must not be treated as a complete filesystem extractor. Files with no hardlinks still incur a canonical name→ordinal map (previously a set) and one Boolean visiting array; larger average-name and hostile-index RSS/CPU need their own release-quality evidence. There are no Windows/macOS hosted results for this new API yet; POSIX filesystem link support varies. Recovery from damaged primary index remains unsupported in this native core. Index integrity is not a third-party signature, and physical payload mutation between operations remains a separate integrity boundary.
