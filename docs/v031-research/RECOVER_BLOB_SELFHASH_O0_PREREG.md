## Primary question
Can public `recover_blob_records(path)`, described in source as returning **valid self-hashed blobs**, list a byte-framed raw blob whose actual content no longer hashes to the returned SHA-256, even while the real Reader refuses the same corruption?

## Frozen predictions
- Control: build real revision-24 archive with deterministic high-entropy RAW member; the API lists its record and its declared SHA; live `CMPCT.read` succeeds; actual payload digest equals declared SHA.
- Mutant: independently flip one non-header byte inside the existing physical RAW payload, preserving its length and BHDR SHA/CRC. `CMPCT.read` must reject. `recover_blob_records` will nevertheless list that same record and report the old declared SHA because it checks only frame bounds.
- Stronger hostile control: append to the same archive a well-framed but unindexed **forged RAW record**, with an arbitrary incorrect digest and CRC, and confirm salvage also presents it (as a candidate) without performing payload authentication. This is intentionally an ordinary record candidate, not a claim it was ever committed.
- Classify inexactly matching fields, parser exceptions, altered legitimate output, and unexpectedly checked digests as a falsification/ambiguous outcome, not a confirmed bypass.

## Strongest simpler control and alternative explanation
Framing-only discovery is a valid fast *candidate enumeration* mechanism, and the source comment may simply overstate its proof class. That alternative is plausible; a scientific negative should distinguish **reported framing candidates** from **cryptographically verified recovered content**. The cheap decisive discriminator is actual SHA256 over physical RAW bytes compared with the claimed API result, plus a real Reader CRC rejection. No full benchmark necessary.

## Product consequence and bounds
If confirmed, downstream consumers must not treat `recover-blobs` metadata as proof of recoverable authentic payload. Two credible bounded product routes: (a) preserve fast scanning but return an explicit `verification_status: unverified` on all candidates; (b) optional bounded `verify_content` tier that validates framing, codec semantics, CRC, SHA and materializes/exporting recovered content only when successful. Neither changes r24 wire bytes; both require hostile decompression budgets and measured RSS/I/O before promotion. Plain SHA metadata does not prove adversarial origin authenticity.
