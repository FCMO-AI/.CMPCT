## Primary question
Can an independently compiled **public C-ABI-only** research client faithfully materialize POSIX flat-file trees whose original inode partitions differ (a hardlink to either of two *different-content* regular files), preserve their literal symlink targets, and share actual Zstd PACK read work, **without** parsing private MessagePack, guessing hardlinks from content, changing native product code, or retaining all regular outputs in memory?

## Baseline / inherited direct evidence
O13/O13b [PR #343](https://github.com/FCMO-AI/.CMPCT/pull/343), exact run 40086479175, proved historical C ABI could not distinguish different terminal hardlink graphs. O14 [PR #349](https://github.com/FCMO-AI/.CMPCT/pull/349), exact run 40090517916, verifies candidate `cmpct_entry_hardlink_owner()` exposes terminal regular-file ordinals and rejects malformed authenticated references. O11 [PR #337](https://github.com/FCMO-AI/.CMPCT/pull/337), exact run 40078228541, measured faster physical Zstd-owner batches with bounded per-group content retention but only reconstructed root regular files, not inode topology. None proves actual C-side filesystem materialization of all three kinds together.

## Hypothesis, stronger controls and alternative explanation
A tiny isolated POSIX C consumer can preflight **all** entries, names, symlink targets, terminal hardlink ordinals, logical size budget and destination emptiness, then emit all regular contents (one verified Zstd physical owner batch at a time, 64-KiB scalar fallback), then create hardlinks via `linkat` and literal symlinks via `symlinkat`. Valid link owners need not precede aliases in archive index order. An independently constructed POSIX source tree plus `os.lstat`/SHA-256 provides stronger oracle than content equality or Python Reader alone. The simpler control is scalar public-C read plus byte-copy aliases, which preserves byte checks but **fails** inode-identity checks. Alternative explanation: Builder ordering accidentally makes a hardlink graph trivial; use independent a/b owner variants, distinct source file bytes and a signed index where alias ordering is not presumed. O15 seeks *correctness*, not an unsafely generalized extraction benchmark.

## Preregistered test / falsification
- Generate two authentic revision-24 Builder archives from distinct regular `a.bin` and `b.bin` bytes, one alias linked to `a.bin` and one to `b.bin`; an additional alias sharing the same terminal inode; literal symlink target differs across variants. Include >=128 related `.txt` small entries to ensure a real compressed PACK; assert actual batch_count > 0 rather than infer eligibility from extensions.
- C client has only the public ABI header and library, no private parse; require valid metadata and fail closed on unsupported entry kinds, unsafe flat names, size overshoots, symlink targets escaping root, missing owner ordinals, duplicate names, or nonempty/preexisting destination. Limit entries and total output; run with fresh private destination.
- Independently compare every resulting regular file and hardlink byte SHA-256 to source; compare *inode equivalence relation*, not inode numbers; compare literal symlink targets and lstat type. Add a preexisting symlink-to-external-canary destination rejection; ensure the canary bytes and destination symlink survive unchanged, with no newly published files.
- Same exact source archive per client and oracle; fingerprint archive, C source and native SHA. Observe counts of pack batch, fallbacks, hardlinks, symlinks, member bytes, and bound stage size. Do not claim O7/O11 performance as O15 result.
- **Kill/narrow:** any mismatch in inode equivalence, symlink targets or bytes, batch count == 0 for intended packed case, acceptance of unsafe input, unbounded staging, canary mutation, or a native ABI difference makes the corresponding claim false; preserve the negative, do not reshape control to pass.

## Scoped semantics / cost / concurrency
This is a **research-only flat POSIX namespace with freshly empty private destination**. It is NOT a secure general extractor, cannot claim TOCTOU safety against malicious concurrent path mutations, filesystem metadata/xattr/ACL fidelity, crash consistency, source-mutation authentication for scalar RAW, Windows/macOS support or transaction atomicity. Source-index SHA commitment is not an external digital signature. Staging allocation <=1 MiB research cap plus 64 KiB scalar buffer and per-entry metadata (RSS to be measured when available). Any failure after publication can leave a partial tree. No code changes to original Reader/Builder/Writer or PR #337. The earlier PR #349 retains ABI ownership; this separate branch owns only its consumer/integration court.
