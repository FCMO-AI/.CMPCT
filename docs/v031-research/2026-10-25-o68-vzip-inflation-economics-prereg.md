## Question and prediction

Can a small legitimate `.zip` source force the O63 real Builder into disproportionate creation CPU and memory *before* a useful virtual-representation decision, and does a stronger simple same-input opaque-storage oracle materially reduce that cost? Prediction: a single highly compressible Deflate member with a small (sub-64 KiB) outer ZIP and 16–24 MiB logical inflated bytes will cause O63's direct `z.read(zi)` and repeated `deflate_level_for(raw,stream)` to reconstruct and recompress substantially more bytes than the physically supplied source. The virtual/opaque side may still reduce output archive bytes; this tradeoff must be reported, not concealed.

## Baseline, counterfactual, falsifiers

- Primary O63 real-product arm: unmodified `Builder(source,workers=1,reproducible=True,reproducible_epoch_ns=0).build(out)` on a physical source containing one ZIP, followed by strong read/verify of the original exact ZIP bytes.
- Simpler charged oracle arm: **same physical source tree**, but in a research-only isolated interpreter replace Builder's imported `make_vzip_recipe` function with a callable returning `None`, forcing the **existing** product's opaque fallback. This is a research oracle, not the original product or a release candidate. Do not claim official product comparison credit.
- Same unique physical ZIP (SHA-256 committed in receipts), same machine/encoding/dependency, identical source paths/metadata. Alternate A/B order and use separate processes; record archive bytes and creation wall+CPU, process peak RSS, selective/full read identity, source bytes and real decoded logical size. Do not conflate fresh process launch with library build time.
- Source ZIP generated by Python stdlib, one Deflate member of deterministic repeated bytes, sizes 64 KiB, 4 MiB and 16 MiB. Cap decompression at 16 MiB, 3 repeats per arm per shape, timeouts and finite per-process address-space limits on POSIX (limits may need platform-specific handling).
- Decision-changing positive: genuine source-bound product shows a >100x expansion ratio **and** a confirmed >5x median create CPU ratio relative to same-tree opaque oracle in the largest shape; this establishes a resource-admission opportunity, not an acceptable hard-coded threshold.
- Kill or narrow: if O63 already bounds inflation before the decode; if same-tree opaque oracle costs nearly as much; if the ZIP arm is not accepted as S_VZIP; if the virtual representation obtains dramatic bytes savings that make admission nontrivial; if the benchmark mechanism alters other source/baseline bytes; or if CI cannot execute source-exact instrument. Preserve all adverse byte and read-latency results.

## BONK / alternative frames

Existing O67 (#423) benchmarks *late unsupported stream rollback*, not ZIP inflation economics. Strongest simpler control is the same-tree opaque fallback; independently compare the actual `S_VZIP` storage choice and reject unmeasured virtual eligibility. Do not buy a full r24/ZIP matrix for a pre-admission bound. Cost exported by opaque: potentially larger archives, lower reuse, lost selective VZIP reconstruction; these are explicit debts. Alternatives, not implemented: bounded per-member and aggregate authenticated inflate budget before `z.read`, early metadata screening subject to distrust of forged ZIP sizes, incremental deflate matching, or a genuine streamed/windowed representation. Preserve generic fallback and exact bytes.
