## Research decision and evidence tier
**Question:** On exactly the same authentic public-Writer 63-DELETE r24 physical A, terminal-checkpoint B, and damaged-terminal recovery C that #853 uses, does #823's *real* owned-decoder Reader admit and reproduce all three accurately; and does its open cost approach B closely enough that B's 4.8–8.4% physical byte tax is hard to justify as a generic remedy?

**Baseline:** #853 observed its own DELETE-only private helper roughly 3.7–6.9x faster than public A and B about 15–20% faster than helper; #823 observed large-N private owned-decoder benefits on a different case. There is **no same-physical cross-class comparison**: separate-host medians cannot be subtracted. This experiment closes that join with unchanged source identities.

**Predictions before execution:** For 4,096 and 8,192 initial files, A has depth 63, B depth 0, C recovers depth 63. All four implementations (unmodified CMPCT, #823 FactoredCMPCT, #823 OwnedCMPCT and #853 OwnedDeleteCMPCT) should reconstruct exactly the same member names and 32-byte content SHA on each A/B/C; no silent fallback for eligible A. We expect OwnedCMPCT/OwnedDeleteCMPCT on A each to be >=2.0x faster than CMPCT A and <=1.50x slower than CMPCT B in warm-open median wall; CPU direction should agree. B has strictly positive physical-byte tax, 4–10% in these families. These are **research hypotheses, not release admission**. The stronger control is existing #853 OwnedDeleteCMPCT because #823's general decoder may pay compatibility work.

**Primary science kill/narrow:** Any source SHA mismatch, actual wire/index/reader content mismatch, C recovery mismatch, unexpected route, missing provider checkout or asynchronous code drift invalidates evidence. If OwnedCMPCT A does not reach the 1.50x checkpoint ratio on both sizes/hosts, narrow the broad "avoid checkpoint bytes" economic claim; do not tune threshold or assume private DELETE-only generalizes. If OwnedDelete beats OwnedCMPCT in a bounded same-state comparison, locate representation/ownership overhead rather than adding checkpoint bytes. Null or mixed results are retained.

**Experiment design:** Three physical archives generated *once per family per host* from original unmodified J24G90 `make_court` inside a second exact-SHA checkout of #853, with all variants measured in one process on the same immutable paths, balanced variant order and raw repeated wall/CPU; physical SHA, signed footer/index, and complete logical bytes checked before timing. Each helper's code inherited from its original source branch, no vendor modifications. Measure complete archive size, original Writer creation wall, warm Reader-open wall/CPU, Python traced allocation, recovery and byte-exact read; keep create/extract and peak RSS as unmeasured if not executed, rather than silently assuming. Small no-CMPCT independent physical SHA/CRC validation of all inputs and a separate receipt validator must reject falsified outcomes. Workflow on Ubuntu and Windows; no full product benchmark unless evidence changes promotion. Setup/install and source checkout costs remain separate.

**Negative controls and alternatives:** Compare same A/B/C across four Reader classes; intentionally corrupt archive SHA/receipt and reject it. Preserve B's genuine speed advantage even when its bytes rise. No synthetic one-pass-only result can be promoted as a public Reader guarantee. Do not silently change the footer predecessor integrity/recovery contract (#857/#869); the experiment uses genuine untouched A/B/C plus C's original known corrupt terminal checksum.

**Potential decision:** A robust <=1.50x product-capable cross-owner parity would prioritize integration of owned replay over a byte-taxed checkpoint. A failure would identify the exact missing semantic/economic boundary and may support checkpoint as a bounded optional strategy. Neither result allows merge/release; metadata, xattrs, hardlinks, hostile graph handling, native parity and whole-system product gate are inherited debts.
