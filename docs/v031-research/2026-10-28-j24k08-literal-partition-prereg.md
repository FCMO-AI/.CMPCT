# J24K08 — signed virtual-ZIP literal-boundary reallocation (prospective falsifier)

Date: 2026-10-28 UTC. **Pre-result research prediction; not a vulnerability/severity or product-release claim.** Exact source parent #642 `78bc1f552fee24970228f89ac25dbf23307b0406`; published v0.30.0/r24 remains intact.

## Question
Is the existing authenticated **physical projection** invariant (`sum(literal lengths)==skeleton usize`, every stream csize matches physical owner, `sum(literals+streams)==logical total`) sufficient to establish byte-for-byte semantic placement for arbitrary selective ranges? Hypothesis: **NO**. Two different virtual-ZIP recipes can satisfy *identical projected size and physical ownership*, but reconstruct different byte sequences and produce wrong-byte correct-length ranges. This is an information/proof-model limit, not an exploited external signature.

## Prospective fixed experiment
Use only the existing independently frozen v24 canonical Deflate-mode0 archive `tests/conformance/v24-virtual-zip-deflate-mode0.json` (Git blob `663b9fdb4df560fb9572fa14bf003928a2379e5e`, archive SHA `9fa44e064af01a2fdc7402881bb89d9449cbc5de6a26563d05f71b812af0c224`). It encodes one payload, two literals `[39,77]`, exact reconstructed size 130 and compressed stream length 14. Move **one byte** from the second literal length to the first (new `[40,76]`), without changing any payload, csize, total, skeleton bytes, blobs, file SHA or recipe SHA/CRC. Recalculate and duplicate the container index and its unkeyed SHA-256 integrity digest in header/footer. Preserve physical data bytes. Freeze only this mutation; no searching corpus after seeing results.

Predict: 1) unchanged golden passes preflight, exact full read/ZIP/SHA/verify; 2) mutated archive **PASSES structural preflight** because all current physical projected lengths match; 3) unchanged logical content digest and CRC make complete read and verify REJECT; 4) a one-byte selective query at offset 39, exactly at the original Deflate stream entrance, returns an incorrect but correct-length byte because the mutated recipe inserts one extra skeleton byte there; 5) other nearby offsets identify precise changed coordinate while no read claims external memory. If any fails, preserve negative and examine actual semantics without changing the prereg.

## Stronger control, alternatives, purpose
The source-level geometry proof is the strongest simpler control for *physical length consistency* and costs only O(recipe entries); it cannot authenticate the **partition geometry / content arrangement** when all lengths are individually legal. Whole-file `rebuild_vzip` CRC+SHA or an independently authenticated proof for requested ranges can distinguish actual bytes; the latter carries proof/metadata cost and is not established by this experiment. Discard the naive statement that ordinary Reader's one-time geometric admission would guarantee SHA-verified random access. Preserve scope: existing `read_range` may have deliberately weaker per-range integrity than `verify`, so this observation by itself is **not** a proven violation of CMPCT's documented API security contract. We test what it can honestly certify.

## Execution and disposition

No benchmark, complexity or product improvement credit. If confirmed, future feature design should separate (A) physical bounds correctness, (B) byte/coordinate provenance, and (C) optional cryptographic range authentication rather than conflate those; no vague remediation without full cost/proof accounting. #638/#642 own VZIP product changes and #645 own skipped-size falsifier; no owner collision on independent literal-boundary proof.
