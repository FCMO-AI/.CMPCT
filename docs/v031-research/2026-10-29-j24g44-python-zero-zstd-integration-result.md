# J24G44 — Python zero-output encoded Zstd physical integrity: implementation record

Date: 2026-10-29 UTC. **Status: experimental product candidate, unmerged.** Read actual HEAD CI and [PR #767](https://github.com/FCMO-AI/.CMPCT/pull/767) for volatile post-commit outcomes.

## Primary question and decision boundary
Can a nonempty compressed Zstd frame with zero claimed logical bytes be physically decoded and rejected when corrupt without changing r24 bytes or breaking inherited zero-coded sentinels? The independent [J24G43 scientific negative #763](https://github.com/FCMO-AI/.CMPCT/pull/763) and [issue #764](https://github.com/FCMO-AI/.CMPCT/issues/764) established Python/Rust false acceptance. J24G44 does not claim to solve native Rust verification.

The prospective hypothesis and kill conditions were committed **before product modification** at `725f900fab315fcae31f038494127436d192db7c`. Main baseline `80c358f8824ec1b20d349c92ed94c898090969b0`, published v0.30.0/r24; existing codec blob `c928e69e1513fa1f7898e4016cbccd8bda3dfbec`.

## Minimal repair
`src/cmpct/native_codec.py` changes only `decompress`, `decompress_using_dict`, `DictDecoder.decompress`. The original early return ignored nonempty encoded frames on `usize==0`. Retain it only for `usize==0 and data==b''`, which preserves the historical empty-encoded sentinel; for nonempty encoded frames use existing package-owned native Zstd ABI with caller-owned destination capacity **one byte** and require exactly zero output. For nonzero claimed sizes reuse the previous real decoding path. The final patch avoids repeated `max()` hot-path calls by computing the capacity once.

No format, packaging ABI, extra Zstd runtime dependency, native crate, Builder/Reader source or frozen evaluator changed. Source `git blob` after hot-path adjustment: `50029f3c9e5dfb1968f53df01f11916883d7ea64`.

## Economic and porting truth
The correct path pays new actual Zstd decoder work for a nonempty physical frame with zero logical bytes. One local Linux `libzstd`/ctypes micro study of 100,000 valid nine-byte empty frames reported median **32.49 microseconds wall / 32.48 microseconds CPU** per call across five groups, and includes Python invocation overhead; that is neither an installed CMPCT throughput benchmark nor controlled same-input release A/B. A separate CPython branch micro favored one conditional capacity assignment over two `max()` calls (~35 ns vs ~81 ns under one local measurement), leading to a low-carrying-cost hot-path simplification. Full stored-byte parity, cold open, create/extract CPU, reader RSS, temp I/O, Windows/macOS cost and 15-row benchmarks are **unmeasured**.
