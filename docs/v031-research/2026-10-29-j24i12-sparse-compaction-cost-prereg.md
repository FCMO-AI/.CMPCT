## Primary question
Does a real authenticated revision-24 archive containing predominantly holes preserve its sparse *physical cost* through compaction, or does the candidate pay resource costs proportional to logical size despite tiny stored bytes?

## Mechanism, stronger controls, alternative explanation
Observed source: `Reader.extractall` uses `ftruncate` plus only sparse data extent writes, and Builder can re-discover sparse extents via `SEEK_DATA/SEEK_HOLE`. But `_compaction_assert_equivalent` calls `source.verify()` and `reconstructed.verify()`, which call `Reader.read()` for S_SPARSE and allocate bytearray(logical size), then bytes(buffer). A separate `file_sha256` call could also materialize sparse data. Expect logical-size-related peak RSS and CPU, even if archive size and scratch disk occupancy stay small. This is a **resource-cost** hypothesis, not a prediction of wrong bytes or sparse materialization to disk.

Strongest simple controls: (i) unmodified Builder from the same sparse filesystem tree to produce original r24 archive; (ii) `shutil.copyfile` of that archive, disclosed as *lower-bound I/O-only control*, not a semantically equivalent compaction because it preserves history; (iii) an identical small metadata/update member to ensure a real committed delta exists. Preserve exact source/output file list, file SHA, real stored bytes, archive/source/destination identities, `S_SPARSE` storage, and physical block occupancy. If sparse physical allocation unexpectedly increases in scratch due to filesystem behavior, classify as physical cost and do not blame Python-only reads without supporting evidence.
