## Primary scientific question and baseline
Can a valid **real Builder-captured sparse per-file extended attribute** remain bound to exactly its intended logical file identity through a physical 63-generation public Writer history mixing renames, deletes, same-name replacements and insertions, and does the J24G64 detached factored oracle reconstruct exactly the Reader's signed effective index? The #808 case used authentic mixed Writer operations but **no deliberately captured physical xattrs**; its synthetic sparse-ordinal tests are not a substitute.

Control A: original unmodified Reader and preflight, plus the source-exact inherited `_apply_journal_ops` once per physical generation. Control B: physical filesystem xattrs read directly from independently materialized extraction, not merely the Reader's index. Control C: source archive built in default metadata-preserving (non-reproducible) mode and xattr snapshot taken **before** any transaction. All outcomes keep the same archive and operation history; no synthetic manually fabricated signed xattr fields.

## Prediction
Where the host offers real xattr capture and restoration, 63 committed one-op mixed journal generations will retain sparse `fsmeta.xattrs` on renamed and replaced paths, omit deleted/changed-identity paths, never transfer an xattr to a newly created homonymous path, and produce identical index bytes for baseline, factored oracle, Reader and preflight. Explicit `require_xattrs=True` extraction must expose precisely the expected xattr key/value on surviving tagged regular files, and no tracked key on surviving untagged files. Expected route: `factored`, not fallback. A stable source SHA and 64 committed footers must be authenticated.

## Scope and constructed population
Linux (ubuntu-24.04) is required; macOS (macos-14) is a separate supported/diagnostic host with a native provider. Windows has no equivalent portable xattr writer and is not counted as xattr support evidence. Use ~128 generated distinct content members with deliberately tagged subsets, then 21 cycles of public `append_rename`, `append_delete`, `append_update`, yielding 63 signed one-op generations and depth 63. Include a renamed tagged original, deleted tagged original, same-name tagged put (must retain), untagged new inserted file (must not inherit), and deletion followed by reinsertion of the **same** name (must not resurrect signed metadata). Keep paths and contents synthetic/public-safe. Validate with original-source exact helper, source-independent physical footer parsing, Reader, preflight, checksum on immutable archive, and strict extracted xattr samples.
