## Decision, inherited controls, and material alternative

O86 is a valid resource admission guard in focused three-host tests: for ZIP members whose *declared* cumulative uncompressed size exceeds 64 MiB per physical ZIP, it rejects speculative VZIP exploration before inflated-member allocations and chooses the existing exact opaque fallback. O68 demonstrated cases that benefit from avoiding speculative inflation, while O71 proved a ratio-only rejection can discard large complete-byte advantages due to cross-object reuse. O86 has **not** yet executed unchanged O63 on the *same above-default-budget source* to measure the cost of refusing VZIP.

**Primary fork:** On an above-64MiB, genuine, reusable high-ratio ZIP cohort with mixed structural/random information, does O86 default guard sacrifice material exact stored-byte gains versus original O63? If so, is the saved create work/RSS enough to motivate preserving an opt-in high-budget choice or a different information/ownership admission frame? This is not a proposal to drop the safety guard. The simpler controls are (a) below-budget structurally similar positive corpus and (b) independent-content above-budget family; both are measured with actual, non-monkeypatched O63 and O86 Builders.

## Prospectively fixed test and hypotheses

- Build fixed-metadata valid Deflate ZIPs by `zipfile.ZipInfo`, with 3 distinct physical ZIPs using Deflate levels 1/6/9, each with **65 MiB** expanded content (above default 64 MiB). Use a fixed-seed mixed structure (repeated semantic-looking bytes plus a 16 KiB random tail), with two ownership cases: identical decompressed payload across ZIPs and independently seeded-but-matched-entropy payloads. Files/metadata independent of exact reuse identity.
- Include the **1 MiB** O71 shared-mixed cohort as a *below-budget positive control*; never use a ratio-only selector. For each exact same physical source, execute real, independently installed O63 baseline and O86 default candidates in fresh subprocesses, alternating AB/BA order. Set identical `workers=1`, reproducible archive mode/epoch and host environment. Distinguish measured `Builder.build()` wall/CPU from fresh-child startup.
- Capture each original ZIP SHA-256, physical bytes, declared expanded bytes, archive SHA-256 and complete bytes, representation kind, process CPU/wall, peak RSS, verify/read/extract latency, and exact reconstructed original bytes. Preserve raw repetitions and environment. Use a bounded per-child timeout. An O86 archive reconstructed exactly is a correctness success even if its size is bigger. Do not claim a product improvement from reduced resource use alone.
- Expected: O86 defaults to opaque above 64 MiB; O63 may exploit *shared* expanded content and produce a smaller complete archive, but this is **uncertain** because historical O71 used 1 MiB and the large Deflate streams, compression policy and selection can change. Below budget, O86 must retain exact O63 bytes. Independent-payload above-budget is a negative control, not automatically a loss.
- **Disproof / narrowing:** if O63 falls back or does not save complete bytes, retire the assumed above-budget VZIP product loss; if O63 has an advantage in the shared case but not independent case, narrow benefit to cross-object identity. If output invalid, source fingerprints diverge, timing sources differ, or installed source identity is wrong, invalidate the experiment. A timeout/OOM on O63 is an *observed resource debt*, not proof that VZIP never has value. A real byte regression cannot be smoothed away by a median.
- The primary resource policy remains bounded speculative work; allowing a 256MiB exploratory control for O86 would mostly replicate O63, so the direct original O63 engine is the strongest true historical control. Do not modify the budget, fallback policy, VZIP code, reader, benchmarks, or release semantics in O88.
